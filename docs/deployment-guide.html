ServerGuard Operations Manual

End-to-end guide for deploying the autonomous AI-Ops platform: from hub setup through node enrollment, monitoring, incident dispatch, and redeployment.

How Monitoring Works

The AI-Ops daemon (ai_ops/daemon.py) runs a continuous loop on every node — both the hub and sub-nodes. Each cycle performs four operations:

Continuous Loop (every 15s)
Discover Containers → Health Check → Record Metrics → Send Heartbeat

Step-by-step lifecycle

Container Discovery (every 4th cycle)

DomainRegistry.discover_and_index_containers() scans all running Docker containers. For each one it classifies the type (web/database/cache/worker/infra), detects exposed ports, resolves the host workspace directory and git repository via CodebaseResolver, and registers the service for monitoring. No public URLs are assigned — discovery is monitoring-only.

Health Check (every cycle)

HealthChecker.check_all_services() inspects each registered service:

  • Docker container state — is it running?
  • OOM kill detection — was it killed by memory exhaustion?
  • Restart delta — did it restart since the last check?
  • Docker HEALTHCHECK status — does the container define a health probe?
  • Log scanning — last 30 lines analyzed by AnomalyClassifier for errors, crashes, stack traces

Log hashes use hashlib.md5 for deterministic dedup across Python runs.

Time-Series Metrics (every cycle)

MetricsStore.record_sample() captures latency (HTTP probe with 5s timeout), memory usage, CPU%, and restart count into a local SQLite database (WAL mode). Every 20 cycles, _check_trends() runs degradation detection:

  • MEMORY_CREEP — memory grew 30%+ and ≥50MB over the window
  • LATENCY_DRIFT — response time increased 50%+ and ≥200ms
  • RESTART_CHURN — 3+ restarts within the window
  • FLAPPING — health flipped 4+ times (unstable service)
Heartbeat to Hub (every cycle)

FleetTelemetryStreamer.send_heartbeat() POSTs node telemetry (services, containers, incidents, memory, trends) to the hub's /api/telemetry/ingest endpoint. The hub response may contain pending commands (restart, resync, purge) which the node executes from a strict whitelist. No inbound ports are required on sub-nodes.

Remediation Tiers

When a health check fails, the RemediationEngine escalates through four levels:

LevelTriggerActionScope
L0 Healthy Observe — clear incident tracking No action
L1 Container stopped/crashed Auto-restart (up to 3 attempts) Container
L2 Network desync (container fell off dev-net) Re-attach to dev-net + reload reverse proxy Network + Proxy
L3 App bug, OOM, repeated crash Create incident dossier → dispatch OpenCode Source code
Multi-Proxy Support
L2 automatically detects which reverse proxy is running — Caddy, Nginx, Apache, or httpd — and sends the correct reload command. Works on servers that already have their own proxy installed.

Telemetry Model

The system uses an outbound-only communication model. Sub-nodes never open inbound ports:

Node → Hub (outbound)
Sub-Node Daemon —POST heartbeat—→ Hub /api/telemetry/ingest
Hub → Node (piggybacked on response)
Hub —pending_commands—→ Sub-Node executes whitelist

Command whitelist — the only actions a hub can request from a node:

CommandWhat it does
restart_container <name>Restart a specific container
resync_network <name>Re-attach container to dev-net + reload proxy
purge_incidentsClear all incident dossiers on the node
Security
Telemetry is authenticated via X-Fleet-Key header. TLS verification is off by default (bootstrap mode) — enable with FLEET_TLS_VERIFY=true for production.

Hub Server Setup

The hub is the central server that runs the Fleet Dashboard and aggregates telemetry from all sub-nodes. Run the setup script:

# Clone the repo on your master server
git clone https://github.com/YOUR_ORG/happy-galileo.git /opt/happy-galileo
cd /opt/happy-galileo

# Run the hub setup script
sudo bash scripts/setup-hub.sh \
  --domain "your-domain.com" \
  --git-name "Your Name" \
  --git-email "you@email.com" \
  --github-token "ghp_YOUR_TOKEN"

What setup-hub.sh does

  1. Installs system packages (Docker, Node.js 20, tmux, git)
  2. Installs OpenCode CLI (npm i -g opencode-ai) and Playwright
  3. Creates the dev-net Docker bridge network
  4. Configures UFW firewall (SSH + HTTP/HTTPS only) and Fail2ban
  5. Installs the devctl CLI into a Python venv
  6. Runs proxy_resolver.sh to detect existing Nginx/Apache/Caddy
  7. Launches the infra stack via docker compose -f infra/docker-compose.infra.yml

After Setup
The dashboard is live at https://status.your-domain.com. The AI-Ops daemon starts monitoring immediately. Run devctl doctor to verify everything is healthy.

Post-setup: get your fleet enrollment credentials

After setup, the hub prints the enrollment command for sub-nodes. You can also find the values in infra/.env:

# These are in infra/.env on the hub
BASE_DOMAIN=your-domain.com
NODE_NAME=hub-hostname
CENTRAL_HUB_URL=              # Empty on the hub itself
FLEET_KEY=your-fleet-key      # Shared secret for node auth

Enroll a Sub-Node

To connect any server (new or already running services) to the fleet, paste this single command:

# Run on the sub-node server (as root)
curl -sSL https://raw.githubusercontent.com/YOUR_ORG/happy-galileo/main/scripts/setup-node.sh \
  | sudo bash -s -- \
    --node-name "vm-02" \
    --domain "vm02.your-domain.com" \
    --hub-url "https://status.your-domain.com/api/telemetry/ingest" \
    --fleet-key "your-fleet-key" \
    --github-token "ghp_YOUR_TOKEN"

What setup-node.sh does

  1. Installs prerequisites (Docker, Node.js, tmux, git)
  2. Clones the repo to /opt/happy-galileo (or pulls latest if exists)
  3. Installs OpenCode CLI + Playwright for autonomous remediation
  4. Creates the dev-net Docker network
  5. Installs devctl CLI with CENTRAL_HUB_URL and FLEET_KEY baked in
  6. Runs proxy_resolver.sh — detects existing Nginx/Apache/Caddy and configures forwarding
  7. Launches the infra stack (Caddy, Dashboard, AI-Ops daemon)
  8. Runs devctl discover — auto-indexes all existing containers, their workspaces, and git repos
  9. Sends initial heartbeat — node appears on the hub dashboard within 15 seconds
Existing Servers
If the server already has services running (Nginx, Apache, Mailcow, any Docker stack), the enrollment script detects them automatically. proxy_resolver.sh configures the existing proxy to forward wildcard traffic to ServerGuard's Caddy, and devctl discover indexes every running container with its workspace path, compose file, and git repository.

Autonomous enrollment flow

What happens after you paste the script
setup-node.sh → Docker + Infra → devctl discover
CodebaseResolver → Labels → Mounts → .git/config
send_heartbeat() → Hub Dashboard → Node appears online

The CodebaseResolver chains three strategies to find each container's source code:

  1. Docker labels — com.docker.compose.project.working_dir (most reliable)
  2. Bind mounts — walks up 3 parent directories from mount sources
  3. Git metadata — reads .git/config for remote URL and .git/HEAD for branch

How OpenCode Fixes Incidents

When L1 (restart) and L2 (network fix) fail, or the failure is an application bug, the system escalates to Level 3:

L3 Escalation Pipeline
Health failure detected → DossierBuilder collects evidence
IncidentBus creates dossier (.json + .md) → Git fix branch created
OpenCode launched in tmux → Autonomous fix → rebuild → verify

What the Incident Dossier contains

  • Container state, restart count, OOM status, exit code
  • Last 50 lines of container logs with extracted stack trace
  • Workspace directory path and Docker Compose file
  • Git branch, commit, and remote URL
  • Resource usage snapshot (CPU, memory)
  • AI-generated fix recommendation based on error pattern

OpenCode autonomous workflow

OpenCode receives the dossier and follows this contract:

  1. Read the error trace and identify the root cause
  2. Edit source code / config to fix the bug
  3. Rebuild and restart: docker compose up -d --build
  4. Expose staging route: devctl expose <service> <port> --env staging
  5. Verify with Playwright: devctl test <service>
  6. Commit and resolve: devctl incident resolve <id> --notes "..."
Monitoring OpenCode
Each dispatch runs in a tmux session named opencode-<incident_id>. You can watch live: tmux attach -t opencode-INC-20260831-A1B2C3. The dashboard's Incident Console also shows worker logs via the API.

Push & Redeploy

To push your latest changes and redeploy on the master server (or any node):

Full platform redeploy

cd /opt/happy-galileo

# Pull latest code
git pull origin main

# Rebuild and restart all infra containers
docker compose -f infra/docker-compose.infra.yml up -d --build

# Verify everything is healthy
devctl doctor

Redeploy a single component

# Just the dashboard
docker compose -f infra/docker-compose.infra.yml up -d --build dashboard

# Just the AI-Ops daemon
docker compose -f infra/docker-compose.infra.yml up -d --build ai-ops

# Just Caddy (after config changes)
docker compose -f infra/docker-compose.infra.yml up -d --build caddy

Force re-discovery of containers

# Re-scan all running containers and update the service registry
devctl discover --force

# Re-index (flushes cached state and rebuilds)
devctl reindex
Zero Downtime
Docker Compose up -d --build performs a rolling restart — existing containers keep running until the new image is ready. The AI-Ops daemon gracefully handles SIGTERM and stops its monitoring loop before exiting.

Troubleshooting

Node not appearing on dashboard

Check

1. Is CENTRAL_HUB_URL set correctly in infra/.env?
2. Can the node reach the hub? curl -k $CENTRAL_HUB_URL
3. Is FLEET_KEY the same on both hub and node?
4. Check daemon logs: docker logs ai-ops-daemon --tail 30

Services not being discovered

Fix

Run devctl discover --force to flush and re-scan. Check that containers are running (docker ps) and connected to dev-net. The daemon auto-discovers every 4th cycle (~60s).

OpenCode not dispatching

Requirements

OpenCode dispatch requires: (1) tmux installed on the host, (2) opencode or npx available, (3) the service workspace must be a real git repo on disk. Check the daemon output for the specific failure reason. If tmux is missing, incidents are still created but marked PREPARED_NOT_DISPATCHED.

False LATENCY_DRIFT warnings

The latency probe timeout was increased to 5 seconds and timeouts are reported as status: -1 (distinct from dead services). If you still see false positives, increase TREND_LATENCY_FACTOR (default 1.5) or TREND_MIN_SAMPLES (default 20) in your environment.

Dashboard shows stale data

The dashboard polls every 4 seconds. If nodes appear offline, check that the heartbeat interval (15s) hasn't been disrupted. Nodes are marked offline after 90 seconds without a heartbeat. Restart the dashboard container: docker restart dashboard.
