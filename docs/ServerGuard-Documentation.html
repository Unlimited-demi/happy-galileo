1. Platform Overview

ServerGuard is an autonomous AI-Ops platform designed for multi-server Docker infrastructure. It provides fleet-wide monitoring, intelligent anomaly detection, and autonomous incident remediation — closing the loop from error detection to code fix to production deployment without human intervention.

What It Does

Fleet Monitoring

Monitors all Docker containers across multiple servers. Collects CPU, memory, disk, and network metrics. Streams telemetry to a central dashboard.

Anomaly Detection

Scans container logs with 17+ multi-language error patterns. Detects Python, Node.js, Go, Java, PHP/Laravel, Ruby stack traces, HTTP 5xx errors, OOM kills, and network failures.

Autonomous Remediation

Dispatches OpenCode AI agent to fix detected errors. The agent checks out a branch, implements the fix, commits, and prepares for human review.

Incident Lifecycle

Complete workflow: detect → classify → fix → verify → merge → deploy. Every incident has a comprehensive dossier with proof of resolution.

Design Principles

  • Outbound-Only Telemetry: Sub-nodes push heartbeats to the hub. No inbound ports required. Commands piggyback on heartbeat responses.
  • Zero Public Ports: All containers communicate over an internal Docker network (dev-net). Caddy handles TLS termination.
  • Safety First: Config backups before writes, nginx -t validation before reload, rollback on failure, mail server detection to avoid breaking Mailcow.
  • Idempotent Operations: Every script checks if work is already done before executing. Safe to run multiple times.
  • Language Agnostic: Grammar-based error detection works across any programming language without hardcoding vendor names.

Data Flow

  1. Collection: AI-Ops daemon on each node inspects containers via Docker socket, scans logs, collects metrics
  2. Detection: Classifier analyzes logs for errors using multi-language grammar patterns
  3. Incident: When error detected, incident created on Incident Bus with full context
  4. Remediation: L1/L2 auto-remediation attempts (restart, network resync). If insufficient, dispatch to OpenCode
  5. Fix: OpenCode checks out branch, implements fix, commits, pushes
  6. Telemetry: Node streams heartbeat with services, incidents, and metrics to hub every 15s
  7. Dashboard: Hub displays fleet-wide status, incidents, and node health in real-time

3. Core Features

3.1 Multi-Language Error Detection

The classifier uses grammar-based syntactic analysis to detect errors across any programming language:

LanguagePatterns DetectedExamples
Python Traceback, File/line frames, exception classes Traceback (most recent call last):
Node.js V8 runtime errors, unhandled rejections, module errors TypeError: Cannot read properties of undefined
Go Goroutine panics, fatal errors goroutine 1 [running]: panic: runtime error
Java/JVM Thread exceptions, caused-by chains, qualified exceptions Exception in thread "main" java.lang.NullPointerException
PHP/Laravel Fatal errors, parse errors, SQLSTATE, application errors [2024-01-15] local.ERROR: SQLSTATE[HY000]
Ruby/Rails Error classes, 500 completions Completed 500 Internal Server Error in 234ms

Additionally detects:

  • HTTP 5xx/429: Upstream server outages and rate limits
  • Network failures: ECONNREFUSED, ETIMEDOUT, ECONNRESET, ENOTFOUND
  • Process crashes: OOMKilled, segmentation faults, fatal errors
  • Config errors: Nginx/Caddy/Apache syntax errors, database auth failures

3.2 Incident Throttling & Contextual Analysis

Prevents incident spam while ensuring critical patterns get attention:

Context TypeTriggerBehavior
Transient Single occurrence Create incident, normal severity
Persistent 3+ same error type Upgrade severity (warning→error, error→critical)
Escalating 5+ incidents in 5 min Force critical severity, bypass throttle

Throttle rule: Maximum 1 incident per service per 5 minutes for the same error type.

3.3 Metrics Collection

Server Metrics

  • CPU load average (1min, 5min, 15min) from /proc/loadavg
  • Memory usage (total, used, available, percentage) from /proc/meminfo
  • Disk usage per mount point (total, used, available, percentage)
  • Network connections (TCP count via ss)
  • System uptime from /proc/uptime

Container Metrics

  • CPU percentage via docker stats
  • Memory used / limit / percentage
  • Network I/O (received / transmitted)
  • Block I/O (read / written)
  • Process count (PIDs)

Metrics are cached for 30 seconds and included in telemetry heartbeats to the central hub.

3.4 Reverse Proxy Detection

Smart detection of existing virtual hosts across all major web servers:

ProxyLocations ScannedDirectives Parsed
Nginx sites-enabled/*, sites-available/*, conf.d/*.conf, nginx.conf server_name, proxy_pass
Apache sites-enabled/*.conf, sites-available/*.conf, conf.d/*.conf ServerName, ServerAlias, ProxyPass
Caddy conf.d/*, Caddyfile, *.caddy Domain blocks, reverse_proxy
Traefik Docker labels traefik.http.routers.*.rule
Env Vars Container environment VIRTUAL_HOST, APP_URL, *_DOMAIN

Each nginx server {} block is parsed separately to correctly map server_name to its corresponding proxy_pass upstream — no cartesian product confusion.

3.5 Safety Features

  • Config backups: Every nginx/Caddy config is backed up before modification
  • Validation: nginx -t before reload, rollback on failure
  • Mail server detection: Auto-skips UFW if Mailcow/Postfix/Dovecot detected
  • Docker port awareness: UFW auto-allows Docker published ports
  • Idempotency: All scripts check if work is already done
  • Vendor domain filtering: Excludes download.redis.io, github.com, etc. from false-positive domain detection

4. Installation & Setup

4.1 Central Hub Setup (Primary Server)

The central hub runs the fleet dashboard and telemetry ingest endpoint. It receives heartbeats from all sub-nodes.

# Clone the repository
git clone https://github.com/Unlimited-demi/happy-galileo.git /opt/happy-galileo
cd /opt/happy-galileo

# Configure environment
cp infra/.env.example infra/.env
# Edit infra/.env:
#   NODE_NAME=Primary Workstation
#   BASE_DOMAIN=dev-server.datakrib.com
#   CADDY_HTTP_PORT=80
#   CADDY_HTTPS_PORT=443
#   CENTRAL_HUB_URL=          (leave empty — this IS the hub)
#   FLEET_KEY=default-fleet-key

# Start the hub
cd infra
docker compose -f docker-compose.infra.yml --env-file .env up -d --build

# Discover local containers
devctl discover --force
Note

The hub's dashboard is accessible at https://status.dev-server.datakrib.com via Caddy's on-demand TLS.

4.2 Sub-Node Enrollment

Sub-nodes run the AI-Ops daemon and stream telemetry to the hub. They can coexist with existing services (nginx, Mailcow, other Docker containers).

# On the sub-node server, run the enrollment script:
curl -sSL https://raw.githubusercontent.com/Unlimited-demi/happy-galileo/master/scripts/setup-node.sh | \
  sudo bash -s -- \
    --node-name "vm2" \
    --domain "vm2.dev-server.datakrib.com" \
    --hub-url "https://status.dev-server.datakrib.com/api/telemetry/ingest" \
    --github-token "ghp_your_token_here"

What the enrollment script does:

  1. Prerequisites: Installs git, curl, ufw, fail2ban, python3, jq
  2. Docker: Installs Docker and Docker Compose if not present
  3. Codebase: Clones the repository to /opt/happy-galileo
  4. Node.js: Installs Node.js 20, Playwright, OpenCode CLI
  5. Docker network: Creates dev-net internal network
  6. devctl CLI: Installs Python venv and CLI wrapper at /usr/local/bin/devctl
  7. Proxy resolution: Detects existing nginx/Caddy/Apache, configures ServerGuard Caddy on internal port (8080+)
  8. Firewall: Runs UFW hardening (skips if mail server detected)
  9. Infrastructure: Builds and starts Caddy + AI-Ops daemon + Dashboard containers
  10. Discovery: Auto-discovers existing Docker containers and registers them for monitoring

6. Monitoring & Detection

6.1 Health Check Signals

The AI-Ops daemon evaluates 6 signals to determine container health:

#SignalSourceIndication
1 Running state Docker inspect Container is running vs stopped/exited
2 OOM kills Docker inspect State.OOMKilled Container was killed due to memory exhaustion
3 Restart count Docker inspect RestartCount Container is crash-looping
4 Docker HEALTHCHECK Docker inspect State.Health.Status Application-level health check result
5 HTTP probe Direct socket to container IP:port HTTP 5xx responses indicate application failure
6 Log scanning Docker logs API + classifier Error patterns, stack traces, exceptions

6.2 HTTP Probing

Even when Docker reports a container as "running", the application inside may be returning 502/503 errors. The health checker resolves the container's IP on the Docker network and sends a direct HTTP request:

Container: aiops-grafana
  Docker IP: 172.18.0.5
  Port: 3000
  Probe: GET http://172.18.0.5:3000/ → HTTP 502 Bad Gateway
  Result: UNHEALTHY (HTTP 502 from aiops-grafana:3000)

Containers in the skip list (ai-ops-daemon, caddy) are not probed to avoid feedback loops.

6.3 Docker Log Parsing

Docker's multiplexed log streams contain 8-byte binary headers per frame:

[stream_type(1), 0, 0, 0, size(4 big-endian)] + frame_data

The log parser reads raw bytes, parses frame headers, extracts frame data, and decodes UTF-8 — all before pattern matching. This prevents corruption from binary headers that would otherwise appear as replacement characters (\\xef\\xbf\\xbd).

6.4 Monitoring Cycle

Every 15 seconds: 1. List all registered services 2. For each service: a. Inspect container (running, OOM, restarts, healthcheck) b. Probe HTTP (direct socket to container IP:port) c. Fetch logs (Docker API, last 100 lines) d. Classify logs (17+ error patterns) e. Determine health status f. If unhealthy: - L1: Auto-restart (max 3 attempts) - L2: Network resync + proxy reload - L3: Dispatch to OpenCode g. Create incident if error detected 3. Collect server & container metrics 4. Stream telemetry to hub (if sub-node)

6.5 Custom Error Patterns

Operators can extend detection without code changes by adding regex patterns to:

~/.devctl/error_patterns.txt    # Lines matching these are flagged as errors
~/.devctl/noise_patterns.txt    # Lines matching these are ignored

Files are re-read every 60 seconds. One regex per line, # for comments.

7. Incident Resolution Workflow

The complete incident lifecycle from detection to production deployment:

01

Detect

AI-Ops daemon scans container logs and detects an error pattern. Creates an incident on the Incident Bus with full context: error snippet, container name, service, severity, and contextual classification (transient/persistent/escalating).

02

Classify & Throttle

Incident throttle checks if this is a duplicate (same service, same error, within 5 minutes). If throttled, the incident is suppressed. If persistent or escalating, severity is upgraded.

03

Auto-Remediate (L1/L2)

If the container is stopped or returning HTTP 5xx, L1 auto-restarts it (max 3 attempts). If the container lost network connectivity, L2 resyncs the Docker network and reloads the proxy.

04

Dispatch to OpenCode (L3)

If auto-remediation is insufficient, the incident is dispatched to the OpenCode AI agent. A comprehensive dossier is generated with error details, logs, workspace path, and instructions.

05

Fix

OpenCode checks out a fix branch (fix/INC-20240901-123456-service), analyzes the code, implements the fix, runs tests, commits, and pushes to the remote.

06

Verify

The fix is deployed locally. DevOps reviews the incident dossier, checks the code changes, and verifies the fix resolves the issue.

07

Merge

DevOps runs devctl merge INC-xxx. The fix branch is merged to master with --no-ff, pushed to remote, and the branch is deleted. The dossier is updated with merge commit and timestamp.

08

Deploy

DevOps runs devctl deploy <service> (or uses --deploy flag with merge). The service is rebuilt and restarted with the merged code. The incident is marked RESOLVED.

9. Tiered Remediation Engine

The remediation engine operates in 4 escalating tiers:

L0 — Observe

TriggerLog anomaly detected, container healthy
ActionCreate incident, record metrics, no automatic action
Use CaseNon-critical warnings, informational errors

L1 — Auto-Restart

TriggerContainer stopped OR HTTP 5xx response
ActionRestart container (max 3 attempts per incident window)
Use CaseOOM kills, crash loops, 502/503 errors
GuardAfter 3 failed restarts, escalate to L2

L2 — Network Resync

TriggerContainer lost Docker network connectivity
ActionDisconnect and reconnect to dev-net, reload proxy (Caddy/nginx/Apache)
Use CaseContainer unreachable on Docker network despite running
GuardIf resync fails, escalate to L3

L3 — OpenCode Escalation

TriggerL1/L2 insufficient, code-level fix required
ActionGenerate incident dossier, dispatch to OpenCode AI agent
Use CaseApplication bugs, null pointer exceptions, logic errors
GuardOpenCode works autonomously in tmux, creates fix branch
Safety

Auto-remediation can be disabled by setting AUTO_REMEDIATION_ENABLED=false in the environment. When disabled, incidents are created but no automatic restart or network resync is attempted.

10.3 Command Channel

The hub can send commands back to nodes via heartbeat responses. Only whitelisted commands are accepted:

CommandAction
restart_containerRestart a specific container
resync_networkDisconnect and reconnect container to dev-net, reload proxy

Security

Arbitrary shell commands are NOT accepted. Only the three whitelisted commands above can be executed remotely. This prevents unauthorized command execution even if the hub is compromised.

11. Troubleshooting

Common Issues

Node appears twice in dashboard (e.g., vm4 and vm-04)

Cause: Inconsistent node naming across enrollment and heartbeat.

Fix: Update all nodes to latest code which normalizes names. Then prune duplicates:

cd /opt/happy-galileo && git reset --hard origin/master
devctl fleet prune --yes

Services show [INTERNAL - NO PUBLIC URL] despite having nginx virtual hosts

Cause: Domain detection not finding the nginx configs.

Fix: Re-run discovery with force:

devctl discover --force

If still not detected, check that nginx configs are in standard locations (/etc/nginx/sites-enabled/, /etc/nginx/conf.d/, /etc/nginx/sites-available/).

Redis/database containers showing vendor URLs (download.redis.io)

Cause: Environment variables like REDIS_DOWNLOAD_URL being picked up as service domains.

Fix: Updated code filters known vendor domains. Update and re-discover:

cd /opt/happy-galileo && git reset --hard origin/master
devctl discover --force

UFW blocked mail ports on Mailcow server

Cause: Older version of UFW script didn't detect mail servers.

Fix: Updated code auto-skips UFW when Mailcow/Postfix/Dovecot detected. If UFW already broke mail:

ufw allow 25/tcp    # SMTP
ufw allow 587/tcp   # Submission
ufw allow 993/tcp   # IMAPS
ufw allow 143/tcp   # IMAP
ufw allow 110/tcp   # POP3
ufw allow 995/tcp   # POP3S

OpenCode doesn't merge fix branch after resolution

Cause: By design — merge requires human confirmation.

Fix: After verifying the fix, run:

devctl merge INC-20240901-123456 --deploy

Dashboard shows stale nodes that no longer exist

Cause: Old node state persisted on disk.

Fix: Prune stale nodes:

devctl fleet prune --max-age 5 --yes
